## Three findings that change the plan

1. **ALAB's checked-in model is Qwen2.5 3B, not 1.5B.** [offlineModelResources.native.ts#L25](https://github.com/jmdada24/interactive-ai-assistant/blob/78480283f13b39cfcf6c7f7624a7087188ce5265/src/ai/offlineModelResources.native.ts#L25) selects 3B quantized, while its README says 1.5B. Both 0.5B and 1.5B are in its "previous models" list (lines 62-66). So its settings and pipeline are not evidence for 1.5B, and the move may mean 1.5B fell short for the author (my inference).
2. **`llama_main` offers less control than ALAB's runtime.** The flags I saw are temperature, `max_new_tokens`, `seq_len`, `cpu_threads`, `prompt_file`, BOS/EOS counts, `warmup` and `ignore_eos` ([main.cpp#L25-L88](https://github.com/pytorch/executorch/blob/ee4b85b4e811c302e0fb1175de4f8b2a189c6055/examples/models/llama/main.cpp#L25-L88)). I saw no top-p, min-p or repetition penalty, so plan for temperature only and handle repetition in validation. `max_new_tokens` is the cap to use, as `seq_len` is deprecated.
3. **No ExecuTorch figures for a Raspberry Pi were found.** The nearest are phone results and secondary llama.cpp reports (see the table). We must measure our own.

## Is UNIVERSAL-OFFLINE-AI a rival?

Possibly, though it is at an early stage: created 3 Nov 2026, 2 commits, 0 stars. Its README has a "Hackathon deliverables mapping", which suggests the same brief, but it does not name the Namma AI hackathon.

**Does well**
- States honestly that it is not ExecuTorch on Raspberry Pi and must be presented as an alternative prototype. We should be just as plain about our own limits.
- Treats the passage as data, not instructions.
- Handles low memory and oversized prompts with clear errors.
- Has a simple offline-proof routine and maps features to the brief's deliverables.
- Offers terminal, desktop and web interfaces (only the terminal code was read).

**Falls short**
- **Fails the brief's core requirement:** llama.cpp with GGUF on a laptop, not ExecuTorch on a Pi.
- **No output validation:** it only checks that the answer is not empty (`app.py` lines 230-231). No parsing, grounding check or pass rate.
- **Partial metrics:** time, tokens/s and model size, with no runtime memory figure.
- **Wrong audience default:** the system prompt targets a first-year college student (line 16). `/level` can adjust this, but nothing targets Class 6-8 or Karnataka.
- **Unsupported claims:** the README cites `tests/` and `arduino/`, but neither appears in the scraped root listing. It also embeds the author's local Windows paths, and `app.py` hard-codes the author's name (lines 109, 115).
- **Scope spread:** coding help, auth and voice, with no sign of evaluation on real passages in what I read.

**Our differentiator:** the exact required stack, source-grounded checks and a measured validation pass rate. In what I read, neither project reports a pass rate.
