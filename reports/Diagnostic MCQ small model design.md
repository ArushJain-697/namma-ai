# A Misconception Library Makes Small Models Diagnostic

Don't ask Qwen3-0.6B to invent misconceptions. Give it a much smaller job. At build time, a strong cloud "teacher" model drafts a library of a few hundred named student misconceptions keyed to NCERT chapters, and we spot-check it by hand. On the device, plain code finds the misconceptions that match the passage. The fine-tuned 0.6B model then does three short, narrow writing jobs: a summary (this already works), an answer plus a question stem for a sentence that code chose, and, for each misconception it is given, the wrong answer a student holding that belief would pick. Code then puts the item together, writes the feedback from the library, and runs it through four verification gates. None of those gates is the same-model check we use today. A strict-JSON (machine-readable text in a fixed format) model output is never trusted on its own. This matters because no published study has shown a model under 7B parameters generating good misconception-based distractors. The strongest results all come from 7-8B models that make the misconception an explicit text step before writing the distractor ([DiVERT](https://arxiv.org/html/2406.19356v2); [MISTAKE](https://arxiv.org/html/2510.11502v1)). Our own baseline shows what happens without that structure: 21% of drafted questions pass (49 of 236), a sixth of the shown questions have a factually wrong key, and no distractor has any diagnostic value. The fine-tuning recipe is plain LoRA on all layers, rank 32, trained in 16-bit on about 2,000 filtered teacher examples. It costs a few dollars of GPU time plus roughly $10-$250 of teacher calls. It exports through the same `optimum-cli` 8da4w path that already works for the base model. The biggest unknowns are whether 0.6B can learn the "apply this misconception" step at all, and how fast anything runs on the Raspberry Pi 5. Measure both in the first hours of the day, not the last.

## Today's pipeline fails because nothing names the student's mistake

Our 12-13 November run of plain Qwen3-0.6B on 40 held-out passages makes the problem concrete. The model drafted 236 questions and 49 passed the checks. The most common reason for holding a draft back was the answer leaking into the question (119 drafts). In a blind rating of the 49 shown questions, 16 were good, 13 ok, 12 bad and 8 had a factually wrong key (`results/eval_qwen3_base/totals.json`, `results/eval_qwen3_base/rating.csv`). The wrong keys are revealing. One stem asked what Ashoka's dhamma was, with the key "religion", even though the passage says it was *not* a new religion. Another keyed Nana Saheb to Jhansi instead of Kanpur. Both are errors of meaning: the word appears in the passage, but the passage does not assert it as the answer. The current same-model answer-back check cannot see these, because the model that wrote the error is the one checking it. Published work confirms this blind spot. Across 14 open models, models failed to correct errors in their own output 64.5% of the time, even though they fixed identical errors shown as someone else's ([arXiv 2507.02778](https://arxiv.org/abs/2507.02778)). As a judge of question-writing flaws, Qwen3-0.6B scored a Cohen's kappa of 0.00 (an agreement score where 0 means no better than chance), the same as always answering "not flawed" ([BenchMarker, arXiv 2602.06221](https://www.arxiv.org/pdf/2602.06221)).

The distractors fail for a different reason. Code picks random passage words, so a wrong pick tells the retention engine nothing. The engine's Bayes detector, concept-graph walk, BKT (Bayesian Knowledge Tracing, a model that estimates whether a student has mastered each concept) and FSRS (a spaced-repetition scheduler) all need each wrong option to point to a misconception id. With random words, that link is empty. The research literature gives a clear diagnosis of what works instead. Every method that matches or beats prompted GPT-4-class models treats the error as an explicit piece of text: generate or retrieve the misconception first, write the distractor *from* it, then check that the two correspond. DiVERT, a fine-tuned 7B model that works this way, matched GPT-4o on distractor match (63.24 vs 60.19 proportional match at 10 candidates). Its written error descriptions were rated 3.07/5 by teachers, against 3.23 for human-written ones and 2.56 for GPT-4o's ([DiVERT](https://arxiv.org/html/2406.19356v2)). A cycle-consistency filter raised an 8B model's distractor precision from 22.56% to 37.14%. That filter keeps a distractor only if inferring a misconception from it and then re-applying that misconception reproduces the same answer ([MISTAKE](https://arxiv.org/html/2510.11502v1)).

Prompting alone does not solve the problem, even with frontier models. In a teacher evaluation of math MCQs (multiple-choice questions), LLM distractors scored 2.68/5 for plausibility against 3.72 for human ones. The authors concluded that LLMs are "less adept at anticipating common errors or misconceptions among real students" ([Feng et al., arXiv 2404.02124](https://arxiv.org/html/2404.02124v3)). Grounding in a curated list helps a great deal when the list covers the topic well. A physics generator given a concept map with misconceptions listed under each node produced 75.20% of items that met all expert quality criteria, against about 37% for plain generation or plain retrieval. Students also guessed its items correctly less often (28.05% vs 37.10%) ([Scaria et al., arXiv 2505.02850](https://arxiv.org/abs/2505.02850v1)). But when GPT-4 was handed a short generic list of 44 errors, it did not beat simple example-based prompting, because the list missed many errors and the model could not tell which ones were common ([Feng et al.](https://arxiv.org/html/2404.02124v3)). The lesson for us: the library must be fine-grained, organised by topic, and retrieved per question.

There is one encouraging sign at our model size. Small models are good at *selecting* from a list, even when they are poor at *inventing*. In the Eedi misconception-mining competition, the efficiency prizes went to a Qwen2.5-0.5B model and to an off-the-shelf 22.7M-parameter MiniLM embedding model for matching wrong answers to library misconceptions ([Eedi](https://www.eedi.com/news/from-wrong-answers-to-real-insights-how-we-used-a-kaggle-challenge-to-map-student-misconceptions)). When Qwen2.5-0.5B answered school MCQs wrongly, it chose the most popular student distractor 51.6% of the time, against 59.3% for a 72B model ([arXiv 2502.15140](https://arxiv.org/html/2502.15140v1)). So the design below gives the 0.6B model only the narrowest generative step and moves everything else into code and the library.

## Code picks the mistake, the model writes the words

The architecture has a build-time half (cloud, done once) and an on-device half (Pi 5, offline). The on-device pipeline is in the table below. "Model" always means the one fine-tuned Qwen3-0.6B `.pte` file, used with different short prompts. Each prompt is a separate, narrow task with a small output, because small models get worse on long, multi-part outputs. Splitting the work into stages also lets code replace whole model calls ([Maity et al., arXiv 2401.07098](https://arxiv.org/abs/2401.07098v1); [Scarlatos et al., arXiv 2405.05144](https://arxiv.org/abs/2405.05144)).

| Step | Who | What happens | Output |
|---|---|---|---|
| 1 | Code | Clean the passage, split it into sentences, read the subject and class if known | sentence list |
| 2 | Code | Retrieve the 1-2 matching library topics and their 5-8 best-matching misconceptions (keyword/BM25 search over each entry's statement and trigger words first; a MiniLM embedding model if keyword recall is poor) | candidate misconception ids |
| 3 | Model, stage S | Write the grade-level summary (unchanged from today; 94/96 rewrites already accepted) | summary sentences |
| 4 | Code | Choose 4-5 evidence sentences: content-dense sentences that mention a retrieved misconception's trigger words | evidence sentences |
| 5 | Model, stage Q | For one evidence sentence: write the answer phrase, then a question stem whose answer is that phrase | `{"answer","stem"}` |
| 6 | Code (L0) | Check the answer is a near-span of the evidence sentence, the stem does not contain it, the stem is a well-formed question; regenerate if not | pass / retry |
| 7 | Model, stage D | Given the stem, answer, evidence sentence and 4-5 labelled beliefs, write the wrong answer each belief would produce | up to 5 candidate options |
| 8 | Code (L0) | Remove duplicates, options equal to the key, banned patterns and length cues; keep the best 3 with *different* misconceptions | 4 options |
| 9 | Verifiers L1-L3 | NLI entailment check, extractive-QA cross-check, blind answer pick on flagged items (next section) | pass / reject |
| 10 | Code | Shuffle the answer position, write the explanation from the evidence sentence and each wrong option's feedback from the library's `fix` text, and assemble the bank JSON the retention engine already reads | question bank |

On the device, the model writes three things: a summary, an answer-plus-stem, and short wrong answers tied to a belief that code gave it. It never picks the answer letter, never writes feedback, never decides which misconceptions exist, and never judges its own work. This is a deliberate split. The library holds the teaching knowledge, the code holds the rules, and the model only handles the wording that code cannot do. A bonus is that the existing `fix` field in the bank format (see `data/banks/photosynthesis.json`) is filled from hand-checked library text rather than model text, so the feedback a student sees is always vetted.

Two smaller choices matter. First, in stage Q the model now picks the answer phrase from a sentence that code chose, instead of code picking a single word. The baseline's keys ("floor", "surfaces", "sliding") were often bare words that could not support a sensible question. The model still cannot drift away from the passage, because the grounding check in step 6 forces the answer back onto the passage text. Second, in stage D the model sees each belief as a short local label (B1-B5) with its statement, never as a global id. Code maps B3 back to `SCI-BIO-PHOTO-002`. This keeps outputs short and makes id hallucination impossible.

### The misconception library is the real product

The library is a JSON-lines file built at build time by the teacher model. It is seeded per NCERT chapter title (titles and learning outcomes are syllabus facts, not copyrighted text). The teacher writes 3-6 misconceptions per chapter, each with an error type and, for science, a pointer to published literature. We then remove near-duplicates using embeddings and hand-check about 10%, which takes about two hours for 300-600 entries. No openly licensed misconception library exists for Indian Class 6-10 science or social studies. The AAAS/BSCS item bank has more than 1,000 misconception-targeted science items ([BSCS](https://assess.bscs.org/science/)), but its terms are unread, so use it only as a source of ideas to paraphrase, never copy it. Social-studies misconceptions have no peer-reviewed Indian source at all. Those entries should come from a taxonomy of error types (chronology slips, confusing similar people or places, confusing institutions, single-cause explanations, confusing similar terms) and be labelled `plausible`, not `lit_supported`. Hold out about 15% of misconception ids from training, so we can test whether the model applies beliefs it has never seen.

```json
{"id": "SCI-BIO-PHOTO-001", "subject": "science", "strand": "biology", "topic": "photosynthesis",
 "grades": [7], "statement": "Plants get their food ready-made from the soil",
 "fix": "Soil gives water and minerals, but the food (glucose) is made inside the leaf.",
 "error_type": "everyday_language", "trigger_cues": ["soil", "roots", "food", "minerals"],
 "concept": "plants_make_food", "prereqs": ["what_is_food"],
 "confidence": "lit_supported", "source": "teacher_generated", "held_out": false}
```

Because ids are stable across passages, the Bayes detector can build evidence about "thinks soil is plant food" across many sessions, not just within one passage. The engine's existing fuzzy matching of free-text misconceptions (`MATCH_RATIO = 0.8` in `src/sakshi/retention/bank.py`) becomes a fallback rather than the main path. If a passage matches no library topic, stage D may emit `"b": "NEW"` with a one-line statement. Code marks that option `"source": "invented"` and allows at most one per item. Invented errors are measurably worse: GPT-4o's were rated 2.56/5 against 3.23 for human ones ([DiVERT](https://arxiv.org/html/2406.19356v2)).

### Field order puts the belief before the wrong answer

A language model writes left to right and cannot go back, so whatever comes first in the output steers what follows. The distractor literature conditions the distractor on the error text written first. Error-first models reach 62.83-63.24 proportional match, against 50.00 for GPT-4o reasoning step by step without a structured error step ([DiVERT](https://arxiv.org/html/2406.19356v2)). In stage Q the answer comes before the stem: the model commits to what is being tested, then writes a question that targets it without repeating it. In stage D each option is written in the order belief label, a short "why" of at most 12 words, then the option text. The JSON should be as small as possible, because strict format constraints measurably hurt reasoning in 8-9B models ([Tam et al., arXiv 2408.02442](https://arxiv.org/html/2408.02442v3)). The "why" field is a cheap ablation candidate: if dropping it doesn't lower quality on the held-out set, drop it to save about 15 tokens per option.

The block below uses `//` comments for illustration; real outputs are plain JSON.

```json
// stage Q, model output
{"answer": "in the leaves", "stem": "Where in a plant does photosynthesis mainly happen?"}

// stage D, model output (beliefs B1-B5 given in the prompt; overgenerate 5, keep 3)
{"options": [
  {"b": "B1", "why": "thinks food comes from soil", "text": "In the soil around the roots"},
  {"b": "B2", "why": "thinks roots eat like a mouth", "text": "In the roots, where food is taken in"},
  {"b": "B4", "why": "confuses storage with making", "text": "In the seeds, where starch is kept"}]}

// final bank item, assembled by code (same shape the retention engine reads today, plus provenance)
{"id": "Q1", "concept": "plants_make_food", "type": "recall",
 "stem": "Where in a plant does photosynthesis mainly happen?",
 "evidence": "It happens mainly in the leaves.",
 "options": [
  {"key": "A", "text": "In the roots, where food is taken in", "correct": false, "misconception": "SCI-BIO-PHOTO-002", "source": "library"},
  {"key": "B", "text": "In the leaves", "correct": true, "misconception": null},
  {"key": "C", "text": "In the soil around the roots", "correct": false, "misconception": "SCI-BIO-PHOTO-001", "source": "library"},
  {"key": "D", "text": "In the seeds, where starch is kept", "correct": false, "misconception": "SCI-BIO-PHOTO-005", "source": "library"}],
 "explanation": "The passage says: \"It happens mainly in the leaves.\"",
 "checks": {"L0": "pass", "nli_key": 0.94, "nli_max_distractor": 0.06, "qa_agrees": true, "blind_margin": null}}
```

Every prompt starts with the passage and ends with the task instruction. Stage Q calls for the same passage then share an identical prefix, so a runtime that can reuse the KV cache (the stored state from the passage tokens) avoids re-reading the passage each time. ExecuTorch `main` has added session primitives for seek, prefill and single-step decode, but whether 1.5.1 includes them is unverified ([PR #19991 mirror](https://gh.r-mj.com/pytorch/executorch/pull/19991)). Stage D prompts do not include the full passage, only the evidence sentence, so they are short anyway. By our arithmetic, a passage needs about 1 summary call, about 4 stage-Q calls, about 4 stage-D calls and a few retries: roughly 10-12 calls and 400-650 output tokens. Today's pipeline makes about 27 calls and writes about 1,240 tokens per passage (1,076 calls and 49,619 tokens over 40 passages). Fewer, shorter calls matter most on slow hardware: on the Cortex-A53 UNO Q, the portable build decodes at 0.37 tokens/s and one passage took 56 minutes (`docs/SUBMISSION.md`).

## Four on-device gates replace the self-check that shares the model's blind spots

Verification should run cheapest first, and hard failures should trigger a regeneration rather than a repair, since showing a wrong key costs far more than throwing away a good item. The table gives the starting design. All thresholds are engineering starting points to be set on our own labelled data, and all Pi 5 timings are estimates scaled from a single DistilBERT benchmark.

| Layer | Tool | What it catches | Pass rule (starting point) | Est. Pi 5 cost |
|---|---|---|---|---|
| L0 code | extend `src/sakshi/checks.py` | answer leak, ungrounded answer, duplicate or near-duplicate options, a distractor equal to or containing the key, "all/none of the above", negated stems, key that is the uniquely longest option, mixed option types or units, negation mismatch between key and evidence | hard rules; soft flags send the item to L3 | 1-20 ms |
| L1 NLI | `cross-encoder/nli-deberta-v3-xsmall`, ONNX Runtime INT8 | key not supported by the passage; a distractor that is also true; a distractor that paraphrases the key | P(entail \| key) ≥ 0.7; every distractor ≤ 0.3; margin ≥ 0.4; reject if key and a distractor entail each other ≥ 0.7 | 0.2-0.5 s per item |
| L2 extractive QA | `deepset/tinyroberta-squad2`, ONNX INT8 | wrong key on fact-style stems (who, where, when, what) | predicted span best matches the key (token-F1 ≥ 0.5) and beats every distractor by ≥ 0.2; skip for why/how stems | 0.1-0.2 s |
| L3 blind pick | the same Qwen3 `.pte`, one forward pass, read option-letter scores with the key hidden and options shuffled | ambiguity, more than one correct answer, on items flagged by L0-L2 only | argmax = key and p(key) − max p(distractor) ≥ 0.2 | one prefill (unmeasured) |

NLI (natural language inference) models answer one question: does sentence A imply sentence B? That makes L1 the only cheap gate that directly tests whether a distractor is also true according to the passage. That is the failure LLM-written distractors show more often: BenchMarker found the share of distractors that were actually correct rose from 10% to 22% when LLMs wrote them ([arXiv 2602.06221](https://www.arxiv.org/pdf/2602.06221)). DeBERTa-v3-xsmall has 70.8M parameters and scores 87.77 on MNLI-mismatched, a standard NLI benchmark ([model card](https://huggingface.co/cross-encoder/nli-deberta-v3-xsmall)). The small version scores no higher (87.55) at more compute ([model card](https://huggingface.co/cross-encoder/nli-deberta-v3-small)). On its own, an off-the-shelf NLI model accepted 82.5% of answerable and rejected 78.5% of unanswerable SQuAD 2.0 questions, an error rate of about 20% in each direction. Combining it with a QA model's confidence worked best ([Chen et al., arXiv 2104.08731](https://ar5iv.labs.arxiv.org/html/2104.08731)). That is why L2 exists. Extractive QA (a model that answers by highlighting a span of the passage) is a differently built second opinion, and round-trip QA filtering is an established method for cleaning synthetic QA data ([Alberti et al., ACL 2019](https://aclanthology.org/P19-1620/)). tinyroberta-squad2 reaches 82.04 F1 on SQuAD 2.0 and can answer "no answer" ([model card](https://huggingface.co/deepset/tinyroberta-squad2)).

These gates map onto our real failures. The dhamma item turns into the hypothesis "Ashoka's dhamma was a religion", which the passage's "not a new religion" contradicts. L0's negation-mismatch flag and L1 should both catch it. For the Nana Saheb item, the QA model should extract "Kanpur" and disagree with the key "Jhansi". These are expectations, not measurements, and verifying them should be one of the first tests. For the runtime, use ONNX Runtime for both encoders. ONNX exports of these models already exist. A DistilBERT encoder ran at about 81 ms per pass with ExecuTorch+XNNPACK on a Raspberry Pi, but at 20.7 s with portable kernels ([Arm Learn](https://learn.arm.com/courses/executorch-on-arm/compare-transformer-inference/evaluate-an-encoder-based-transformer-deployment/view-the-distilbert-benchmark-results/)), and nobody has confirmed that DeBERTa's attention exports cleanly through ExecuTorch. The two encoders add roughly 0.3-0.5 GB of memory beside a model whose measured peak is 1.7-2.5 GB, which fits easily in 8 GB.

Rule-based checks deserve their place at the front. A 19-rule item-writing-flaw detector matched 90.87% of human labels, against 78.89% for GPT-4, but both were weak on "more than one correct answer", so semantic gates are still needed behind them ([Moore et al., arXiv 2307.08161](https://arxiv.org/pdf/2307.08161)). L3 changes our same-model check in two ways. It no longer asks the model to write an answer, and it hides the key and shuffles the options. Its score then becomes a continuous margin rather than a yes/no, and it runs only on the 10-30% of items flagged earlier, because it costs a full prefill. Never use the 0.6B model as a free-form judge of quality. An optional L4 copies the MISTAKE cycle idea: show the model one kept distractor and the five beliefs, read which label it picks, and lower an item's diagnostic score if it doesn't pick the belief the option is tagged with. This checks that the option matches its misconception, not that the facts are right, which is exactly where a shared-model check is least harmful.

When an item fails, work down a fixed ladder. First, regenerate up to twice with a different evidence sentence. Next, build a code-only "which statement is true according to the passage?" item: the key is the evidence sentence (or the library's correct conception) and the distractors are the library's misconception statements for that topic, gated by L1 to make sure the passage does not support them. This is diagnostic by construction. Next comes the existing fill-in-the-blank item, marked non-diagnostic (misconception `null`) so the engine doesn't treat it as evidence. Then a pre-verified item from an offline bank built with the same gates plus human review. Finally, show fewer questions. The rule throughout is to show nothing rather than show an item with a wrong key. Before trusting the thresholds, label about 200 generated items for wrong key, more than one correct answer and malformed (the 49 rated baseline items are a start). Then tune L1 until no more than 2-3% of wrong-key or multiple-correct items get through, and report the rejection rate that results.

## Two thousand filtered examples from a frontier teacher, none from NCERT text

No paper measures how much data a sub-1B model needs for this exact task. The nearest evidence comes from curated-data studies (LIMA, s1, LIMO, Deita). It says that around 1,000-3,000 diverse, high-quality examples teach format and behaviour, and that diversity matters more than volume ([LIMA, arXiv 2305.11206](https://arxiv.org/abs/2305.11206); [Deita, arXiv 2312.15685](https://arxiv.org/abs/2312.15685)). Students of about 3B parameters or smaller also learn better from short teacher outputs than from long chains of reasoning ([arXiv 2502.12143](https://arxiv.org/abs/2502.12143)). Target about 2,000 accepted passages spread over 150-250 NCERT topics across both subjects and Classes 6-10, capped at 10-15 per topic. Generate about 3,000, because layered filtering should discard 25-40% (our estimate; no published rejection rates exist for this kind of pipeline). Before generating anything, train checkpoints at 500, 1,000 and 2,000 examples and plot held-out quality. If the curve is flat after 1,000, spend the remaining time on diversity and filtering instead of more data.

Licences shape the source mix. NCERT allows downloading and personal or reference use but forbids republication, and a June 2026 notice warned that unauthorised digital circulation is punishable under the Copyright Act ([Careers360](https://news.careers360.com/ncert-warns-publishers-against-copyright-infringement-of-school-textbooks-educational-materials)). Use NCERT only as a topic list and never commit its text. Students can still paste their own NCERT pages at run time. The mix should be about 50% teacher-written synthetic passages generated from the NCERT topic list. This is the only scalable source of Indian history, civics and geography text, and it carries no licence risk. Vary the style per passage (textbook, teacher notes, story, children's newspaper) and fact-check each passage with a second model, because dates and names in history are where synthetic text goes wrong. Add about 25% OpenStax excerpts (CC BY 4.0, but check each title) or Simple English Wikipedia (CC BY-SA 4.0) ([OpenStax licence](https://openstax.org/license); [Wikipedia copyrights](https://simple.wikipedia.org/wiki/Wikipedia:Copyrights)), about 15% FineWeb-Edu passages filtered to school topics (ODC-By) ([dataset](https://huggingface.co/datasets/HuggingFaceFW/fineweb-edu)), and about 10% SciQ support paragraphs, which are CC BY-NC 3.0, so keep them in a separate shard that can be removed ([SciQ card](https://huggingface.co/datasets/allenai/sciq/blob/main/README.md)). Avoid OpenBookQA, whose data licence is listed as unknown ([card](https://huggingface.co/datasets/allenai/openbookqa/blame/main/README.md)). Give every row `source` and `licence` fields. Also include a few noisy OCR-style and bullet-note passages, because real users will paste messy text.

The teacher call runs once per passage and returns the full worked item. Code then slices it into the student's short training tasks. The prompt gives the teacher a role (an experienced CBSE teacher writing *diagnostic* items, working with a misconception researcher), the passage, grade and subject, and the 5-8 library misconceptions retrieved for the topic. It then fixes the order of work. Write a 3-5 sentence summary. Choose 2-3 testable ideas and quote the supporting sentence for each. Write the answer, then the stem. For each of five candidate distractors, name the belief label (or `NEW` plus a statement) *first*, then the short why, then the option text. Finish with a self-check: could any distractor also be defended from the passage, and could the answer be guessed without it? Constraints are four options in the final item, similar length and grammar across options, no "all/none of the above", no negated stems, Indian context and units, and no answer letters (code shuffles). The teacher's scratch work (idea selection, self-check) is dropped from the student's targets. Asking for five distractors and keeping three is the overgenerate-and-rank pattern, which lifted a fine-tuned 7B model to the level of GPT-4 with step-by-step reasoning ([Scarlatos et al.](https://arxiv.org/abs/2405.05144)).

For the teacher, use the strongest frontier model you have access to for the library and the items, a cheap model for passage drafts, and a model from a *different* family as judge, which reduces a model's bias towards its own output. At 2026 aggregator list prices, 2,500 item calls (about 5M input and 3.75M output tokens) cost roughly $2 on DeepSeek V3.2, $7 on Gemini 3.1 Flash-Lite, $41 on Gemini 3.5 Flash, $69 on GPT-5.4 and $119 on Claude Opus 4.8. Add 30-50% for passage drafting and the judge pass, and subtract up to about half with batch APIs. The aggregator sources disagree on names and prices, so check vendor pages first ([BenchLM](https://benchlm.ai/llm-pricing)). At 10-30 parallel requests, generation takes under an hour. Read each provider's terms on training models with its outputs before committing data to a public repo.

Filter in order of cost, cheapest first. First, schema and rules: valid JSON, unique options, key among the options, evidence quote a literal substring of the passage, no answer leak. Second, run the same L1 NLI and L2 QA gates the device will use. That way the student only learns from items that would pass on the device, and the filter doubles as a test of the gates. Third, run an MQAG-style entropy check that rejects items whose answer distribution is split between the key and a distractor ([MQAG, arXiv 2301.12307](https://arxiv.org/pdf/2301.12307)). Fourth, have the different-family judge score each item from 1 to 5 on grade fit, factual correctness, stem clarity, distractor plausibility, distractor-to-misconception match, explanation correctness and Indian context. Keep items where every score is at least 3 and the mean is at least 4. Fifth, remove near-duplicates with MinHash (a fast text-fingerprint method) at Jaccard ≥ 0.7, plus an embedding similarity cut at cosine ≥ 0.92 for synthetic passages, which tend to paraphrase each other. Last, check reading level loosely. Log every rejection reason, and hand-review about 100 accepted and 50 rejected items to estimate how accurate the filter is.

From each accepted passage, build about 2-3 stage-Q rows and 2-3 stage-D rows, plus stage-S summary rows for about 15% of passages so the summary skill doesn't degrade. That gives roughly 5,000 Q rows of about 500 tokens, 5,000 D rows of about 250 tokens and 300 S rows: about 3.9M tokens per epoch by our arithmetic. Keep the held-out set clean in four ways. Set aside 10-15% of NCERT chapters before generating anything, and generate no training text for them. Hold out one real-text source slice. Hold out 15% of misconception ids. Freeze the existing 40 passages in `data/passages/eval/passages.jsonl` with a SHA256 manifest. Then run MinHash (Jaccard ≥ 0.5) and embedding (cosine ≥ 0.85) decontamination between every training passage or stem and every eval one, and drop the *training* side on any match. Generate eval items with a different prompt seed, and ideally a different teacher, so the student isn't rewarded for copying one teacher's style.

## Plain LoRA on all layers trains in under an hour on a free T4

LoRA freezes the original model and trains a small add-on set of weights. "Rank" sets the size of the add-on. Several variants exist (rsLoRA, DoRA, LoRA+, PiSSA), but none is a reliable improvement for this task. A 2025 sweep across Llama and Qwen models found that LoRA matches full fine-tuning on small and medium datasets as long as it is applied to *all* linear layers. Attention-only LoRA "significantly underperforms" ([Thinking Machines](https://thinkingmachines.ai/blog/lora/)). PiSSA showed the largest loss of general ability in a 2026 comparison (−22.19 points against −7.75 for plain LoRA on Qwen2.5-7B) ([PEFT-Arena, arXiv 2605.28819](https://arxiv.org/html/2605.28819)), and it changes the base weights, which complicates export. DoRA adds latency for no proven gain. Use 16-bit LoRA, not QLoRA. Qwen3-0.6B is unusually sensitive to 4-bit rounding ([arXiv 2505.02214](https://arxiv.org/html/2505.02214v1)), the bf16 weights need only about 1.2 GB, and training on a 4-bit base would create a mismatch with the weights we merge into. Unsloth's Qwen3 notebook defaults to `load_in_4bit=True`, so set it to False.

```python
from peft import LoraConfig
from trl import SFTConfig, SFTTrainer

peft_config = LoraConfig(
    r=32, lora_alpha=32,            # ~20M trainable weights, about 3% of the model (our arithmetic)
    lora_dropout=0.05,
    target_modules="all-linear",    # q,k,v,o,gate,up,down; never attention-only
    task_type="CAUSAL_LM",
)
args = SFTConfig(
    learning_rate=2e-4,             # LoRA wants ~10x the full-fine-tune rate; sweep 1e-4/2e-4/3e-4 on an A100
    lr_scheduler_type="cosine", warmup_ratio=0.05,
    num_train_epochs=2,             # up to 3; pick the checkpoint by held-out JSON validity and pass rate
    per_device_train_batch_size=4, gradient_accumulation_steps=4,   # effective batch 16 (keep < 32)
    weight_decay=0.01,
    max_length=2048,                # TRL's default 1024 truncates the END of the example, i.e. the JSON
    completion_only_loss=True,      # learn only the answer, never the prompt
    packing=False,
    fp16=True, bf16=False,          # T4 has no bf16; on an A100 flip these
    gradient_checkpointing=True,
    eval_strategy="steps", eval_steps=50, save_steps=50,
    seed=3407,
)
```

These settings follow published guidance. The best LoRA learning rate is consistently about 10x the full-fine-tuning rate, LoRA tolerates large batches poorly, and effective batch should stay below 32 ([Thinking Machines](https://thinkingmachines.ai/blog/lora/); [TRL guide](https://huggingface.co/docs/trl/main/en/lora_without_regret)). TRL's `max_length` defaults to 1,024 and cuts off the end of each example ([TRL SFT docs](https://huggingface.co/docs/trl/main/en/sft_trainer)). Training loss below about 0.2 signals overfitting ([Unsloth guide](https://unsloth.ai/docs/get-started/fine-tuning-llms-guide/lora-hyperparameters-guide)). With short, templated outputs, loss falls quickly, so choose checkpoints by held-out schema validity and verified pass rate, not by loss.

The single most likely silent bug is a mismatch between the training prompt and the device prompt. Train in Qwen3's non-thinking format. Build each prompt with `tokenizer.apply_chat_template(msgs, add_generation_prompt=True, enable_thinking=False, tokenize=False)`, which ends in an empty `<think>\n\n</think>\n\n` block, and make the completion the JSON plus `<|im_end|>`. Hard-code that exact rendered string in the device runner ([Qwen3 tokenizer_config](https://huggingface.co/Qwen/Qwen3-0.6B/raw/main/tokenizer_config.json)). Decode one training sample's unmasked labels to confirm that only the JSON and the end token are trained. Decode greedily on the device. Qwen's suggested temperature of 0.7 is meant for open chat ([model card](https://huggingface.co/Qwen/Qwen3-0.6B)).

None of the times below has been measured; they are estimates from compute (FLOP) arithmetic. Check them with a 20-step timing run before committing to a plan.

| Run | Colab T4 (free) | A100 | Cost |
|---|---|---|---|
| 0.6B, about 3.9M tokens/epoch × 2 | about 30-50 min | about 5-10 min | free, or under $1 |
| 0.6B, 3-point learning-rate sweep | not advised | about 20-30 min | about $1 |
| 1.7B fallback, same data | about 1.5-3 h (risk of disconnection; save checkpoints to Drive) | about 15-30 min | about $1 |

The timings are compute arithmetic (about 6 × parameters × tokens, at realistic rather than peak GPU throughput). The only published anecdote is a Qwen 0.6B classifier fine-tune that took 18 minutes ([PromptZone](https://www.promptzone.com/samir_hansen/fine-tuning-qwen-06b-for-local-question-categorization-4djc)). Peak memory is set mostly by the 152k-token vocabulary's output scores, not by the weights, so batch 4 with gradient checkpointing should fit a 16 GB T4. A100 rental is typically $1-2 per hour, but we did not check current rates. Skip DPO and ORPO on the build day. These preference-training methods teach the model from good/bad pairs. A 2026 study found DPO "is not a reliable large win over a well-tuned SFT baseline" at small scale ([arXiv 2603.20100](https://arxiv.org/abs/2603.20100)), and building clean preference pairs costs analyst time we don't have. If time is left, a better use is rejection sampling: let the fine-tuned model generate several outputs for the training passages, keep the ones that pass all gates, and train a second round on them. The logged rejections can become DPO pairs later.

### Export uses the path that already works, with a quality diff at each step

Merge the adapter into a **bf16** base, never a 4-bit one: `PeftModel.from_pretrained(base, adapter).merge_and_unload()`, then save the model and tokenizer to one directory. Export with the command that already works for the base model, passing the group size explicitly:

```bash
optimum-cli export executorch --model ./merged --task text-generation --recipe xnnpack \
  --use_custom_sdpa --use_custom_kv_cache --qlinear 8da4w --qlinear_group_size 32 \
  --qembedding 8w --max_seq_len 1024 --output_dir ./out
```

8da4w means 8-bit dynamic activations and 4-bit weights. Weights are stored in groups of 32, and each group shares one scale factor. Run `optimum-cli export executorch --help` first. The `--qlinear_group_size` and `8da4w,8da8w` fallback flags were confirmed only on `main`, not the 1.1.0 tag ([optimum-executorch CLI](https://raw.githubusercontent.com/huggingface/optimum-executorch/main/optimum/commands/export/executorch.py)). Ship `tokenizer.json` next to the `.pte`, because the tokenizer is not packaged inside it. Expect a measurable hit from 4-bit post-training quantization (PTQ, rounding the weights after training). On Qwen3-0.6B, 8-bit weights are lossless, but 4-bit with group size 128 drops MMLU (a general-knowledge benchmark) from 47.1 to 42.1-44.0 ([arXiv 2505.02214](https://arxiv.org/html/2505.02214v1)). The closest test of exactly this scheme is Llama-3.2-1B with plain 8da4w PTQ. There, the scores most relevant to strict output formats fell hardest: instruction following (IFEval) from 59.5 to 51.5, and function calling (BFCL) from 25.7 to 14.3 ([Llama-3.2-1B card](https://huggingface.co/meta-llama/Llama-3.2-1B-Instruct)). So measure JSON validity and verified pass rate on the merged bf16 model and again on the `.pte`. If the `.pte` loses more than about 2 points, export `--qlinear 8da8w` for the 0.6B model: close to lossless, but a larger file and slower decoding.

Quantization-aware training (QAT) is the stretch option, not a day-one task. It simulates the 4-bit rounding during training so the weights learn to tolerate it. Meta's QAT+LoRA closed almost the whole gap on Llama-3.2-1B under this exact scheme (MMLU 49.0 against 49.3 for bf16 and 43.3 for plain PTQ) ([card](https://huggingface.co/meta-llama/Llama-3.2-1B-Instruct)). But optimum-executorch has no code path for a checkpoint that is already quantized ([quantization.py](https://raw.githubusercontent.com/huggingface/optimum-executorch/main/optimum/exporters/executorch/quantization.py)). An exact match therefore requires the `convert_weights` + `export_llama` route that Unsloth documents, and Unsloth pins torchao 0.14.0 ([Unsloth phone deploy](https://unsloth.ai/docs/basics/inference-and-deployment/deploy-llms-phone)). That version conflict is not worth risking in one day. Keep the merged single `.pte`. ExecuTorch's native LoRA format (a 473 MB shared base plus 39 MB adapters) only pays off when several adapters share one device ([executorch-examples](https://raw.githubusercontent.com/meta-pytorch/executorch-examples/main/program-data-separation/cpp/lora_example/README.md)).

ExecuTorch ships no JSON grammar engine. A `LogitProcessor` hook (a place to modify token scores before sampling) was merged to `main` on 15 May 2026 for exactly this purpose, but it may not be in 1.5.1 ([PR #19517](https://github.com/pytorch/executorch/pull/19517)). So rely on fine-tuning plus parse-and-retry for JSON, and read option-letter scores directly for L3. On speed, nobody has published ExecuTorch numbers for Qwen3 on a Pi 5. The Pi 5's Cortex-A76 cores support the dot-product instructions (SDOT) that the KleidiAI int4 kernels use ([PyTorch blog](https://pytorch.org/blog/bringing-generative-ai-to-the-masses-with-executorch-and-kleidiai/)). The A53 crash should therefore not recur, and the custom-SDPA/KV-cache export should load. Our unmeasured guess is low tens of tokens per second for decoding on 0.6B, and under half that for 1.7B.

## A twelve-hour build day, ordered by what could sink it

The plan front-loads the two unknowns that could change the design: Pi 5 speed, and whether 0.6B learns stage D. Each block has an exit check. The device track can run while generation and training jobs run in the background.

| Time | Data and model track | Device and code track | Exit check |
|---|---|---|---|
| 09:00-10:00 | Freeze the 40 eval passages (SHA256) and the held-out chapter list; write the teacher prompt and try it on 10 passages | Build the runner natively on the Pi 5 with XNNPACK+KleidiAI; benchmark base 0.6B 8da4w prefill and decode at a 400-token prompt; confirm custom ops load | Pi tok/s recorded; eval frozen |
| 10:00-11:00 | Teacher drafts the misconception library per chapter; deduplicate; hand-check 10%; mark 15% of ids held out | Add the new L0 rules to `checks.py` (grounding, leak, negation mismatch, option homogeneity) with one seeded failure test per rule | Library of 300-600 ids |
| 11:00-12:30 | Generate about 3,000 passages and items at 10-30 parallel requests; judge pass | Export NLI-xsmall and tinyroberta to ONNX INT8; time both on the Pi with the LLM loaded | Raw data in; encoder timings |
| 12:30-13:30 | Filter, deduplicate, decontaminate, split; slice into S/Q/D rows; assert nothing is truncated; decode one label mask | Library retrieval (BM25 over statements and cues); bank assembler that writes the retention-engine JSON | Train file ready |
| 13:30-14:30 | Train 0.6B (A100: learning-rate sweep; T4: one config); start 1.7B in the background as insurance | Fallback ladder, including the code-only "which is true" item | Checkpoints saved |
| 14:30-15:30 | Evaluate checkpoints in HF bf16 on the 40 passages and the topic-disjoint held-out set; choose best | Label about 200 items (start from the 49 rated) and calibrate L1/L2 thresholds | Go/no-go on 0.6B |
| 15:30-16:30 | Merge, export 8da4w; compare `.pte` against bf16 on 20 prompts | Copy the `.pte` and encoders to the Pi; run 5 passages end to end | Quantization loss ≤ 2 pts, else export 8da8w |
| 16:30-18:00 | Full 40-passage run through the new pipeline (Mac `.pte`); collect shown items | Pi timing on 5-10 passages; memory and thermal log | Metrics table filled |
| 18:00-19:30 | Blind human rating of baseline and new shown items mixed together | | Ratings done |
| 19:30-21:00 | Contingency: 1.7B swap, 8da8w, or prompt fixes; write up numbers | | Decision recorded |

Go/no-go rule for 1.7B: switch if the fine-tuned 0.6B misses the targets in the next section on held-out data after verification. In particular, switch if fewer than half of items have at least two distractors that a rater judges a believable product of their tagged misconception. Qwen3-1.7B starts higher on general ability and keeps more of it under 4-bit quantization (MMLU 60.0 falling to 55.7) ([arXiv 2505.02214](https://arxiv.org/html/2505.02214v1)). It costs more memory and roughly half the decode speed.

## Measure on the frozen 40 passages with blind human rating

Run the before and after numbers through the same 40 passages and the same gates, then add the larger topic-disjoint held-out set for the automatic metrics. Shuffle baseline and new shown items together, with sources hidden, so the rater cannot tell which pipeline wrote which item. If possible, use two raters and report how often they agree; crowd and expert raters disagree on MCQ quality about 25% of the time ([BenchMarker](https://www.arxiv.org/pdf/2602.06221)). Add one diagnostic question to the rubric for every wrong option: "If a student picked this, would you believe they hold misconception X?" The targets below are our proposals, not literature values.

| Metric | Baseline (12-13 Nov) | Target | How measured |
|---|---|---|---|
| Model-drafted items passing all gates | 49 / 236 (21%) | ≥ 50% | pipeline log |
| Drafts held back for answer leak | 119 / 236 (50%) | ≤ 10% | L0 log |
| Shown items with a wrong key | 8 / 49 (16%) | ≤ 2% | blind rating |
| Shown items rated good or ok | 29 / 49 (59%) | ≥ 75% | blind rating |
| Wrong options tied to a library misconception | 0% | ≥ 90% | bank JSON |
| Items with ≥ 2 options rated "believable for misconception X" | 0% | ≥ 60% | blind rating |
| Model share of shown items | 49 / 122 (40%) | ≥ 80% | pipeline log |
| Summary rewrites accepted | 94 / 96 | no drop | existing checks |
| JSON parse rate, bf16 vs `.pte` | n/a | ≥ 98%, gap ≤ 2 pts | parser |
| Calls and output tokens per passage | about 27 and about 1,240 | ≤ 12 and ≤ 700 | runner log |
| Seconds per passage, M4 and Pi 5 | 19.1 s (M4); Pi not measured | report p50/p95 | runner log |
| Gate false-accept on labelled wrong-key/multiple-correct items | not measured | ≤ 3% | calibration set |

Forty passages is a small sample. With 49 rated items, the 16% wrong-key rate has a 95% confidence interval of roughly ±10 points (our binomial arithmetic). Only large changes will be clear on the 40-passage set, which is why the 300-item topic-disjoint set should carry the automatic metrics. An LLM judge can extend human rating to that larger set, but even GPT-5 reaches only κ 0.50 against humans on flaw detection ([BenchMarker](https://www.arxiv.org/pdf/2602.06221)), so treat it as a screen, not as ground truth. Measure quantization loss separately (merged bf16 against `.pte` on identical prompts), so that export bugs aren't blamed on the model.

## The biggest risk is that no one has shown a 0.6B model can do this

Every result on generating misconception-based distractors uses 7B or larger models, almost all on a single UK maths dataset ([DiVERT](https://arxiv.org/html/2406.19356v2); [LookAlike](https://arxiv.org/html/2505.01903v2)). Whether 0.6B can turn "thinks food comes from soil" into a fitting wrong answer for a new passage is the central open question. The design limits the damage if it can't. Stage D is the only step that needs this skill, the 1.7B fallback uses the same data, and the code-only "which statement is true" item keeps diagnosis working even if stage D fails completely. There is also a subtle interaction to watch. Training a model on misconception answers has been shown to weaken its correct problem-solving ([Sonkar et al., arXiv 2410.12294](https://arxiv.org/abs/2410.12294v1)). Keep stage Q (correct answers) and stage D (wrong answers) as clearly separate prompts, and watch the wrong-key rate after fine-tuning.

| Risk | Why it matters | Mitigation |
|---|---|---|
| Teacher distractors don't reflect real student errors | LLM distractors score 2.68 vs 3.72 on plausibility ([Feng et al.](https://arxiv.org/html/2404.02124v3)) | Library-first, with literature-backed entries marked; validate later with real student choices |
| Social-studies library has no research base | All entries are `plausible`, not evidenced | Error-type taxonomy; hand-check; report subjects separately |
| Synthetic history text hallucinates | Wrong facts get trained in as keys | Second-model fact check; topic cap; real-text shard |
| 4-bit export breaks format | IFEval −8, BFCL −11 on Llama-3.2-1B ([card](https://huggingface.co/meta-llama/Llama-3.2-1B-Instruct)) | bf16-vs-`.pte` diff; 8da8w fallback; QAT later |
| Pi 5 is slow or hits an XNNPACK int4 bug | One unverified Pi 5 report showed Gemma at 0.87 tok/s on ExecuTorch vs 6.71 tok/s on llama.cpp ([dev.to, page now 404](https://dev.to/bamb00boy/first-gemma-4-executorch-deployment-on-raspberry-pi-5-and-why-its-77x-slower-than-llamacpp-gmb)) | Benchmark in hour 1; generate the next question while the student reads the current one |
| Gates reject too many good items | NLI is wrong about 20% of the time in each direction; rules over-flag (2.1 vs 1.6 flaws per item) ([Chen et al.](https://ar5iv.labs.arxiv.org/html/2104.08731); [Moore et al.](https://arxiv.org/pdf/2307.08161)) | Calibrate on 200 labelled items; regenerate rather than block |
| Version drift in optimum 1.1.0 / ExecuTorch 1.5.1 | Flags and hooks confirmed only on `main` | `--help` check in hour 1; keep the proven base-export command |
| Prompt template mismatch | Silent quality loss bigger than quantization | One rendered template string shared by training and runner |
| Licence or terms exposure | NCERT forbids republication; SciQ is non-commercial | Topic list only; per-row licence field; separate NC shard; read provider terms |

## Conclusion

The point is not that a 0.6B model can be taught to diagnose students. It's that a hand-checked misconception library with stable ids carries the diagnosis, and the model's job is reduced to writing the words. That changes where effort pays off. An hour spent improving library coverage or the verification gates helps every future model, including a 1.7B swap or a better small model next year. An hour spent tuning LoRA settings helps only this checkpoint. It also means the verification stack (code rules, NLI, extractive QA, a blind pick) does three jobs: it filters the teacher's data, it gates items on the device, and it measures improvement.

Even the best-run version of this plan can only show that items are *plausibly* diagnostic. Every number in the measurement table comes from teachers' or models' judgment. The real test is whether students who pick option C actually hold misconception C. The best evidence in the field comes from rankers trained on how often real students choose each option ([Scarlatos et al.](https://arxiv.org/abs/2405.05144)). The retention engine's Bayes detector will start collecting exactly that data the moment items carry library ids. The next step after this build day is to close that loop: drop or rewrite misconceptions that students never pick, and use the misconceptions they do pick to decide which library entries matter.
